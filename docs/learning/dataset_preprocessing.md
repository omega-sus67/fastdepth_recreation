# Dataset and preprocessing

## Diverse NYU-derived sample — 14 November

**Question.** Earlier work had 128 training frames from only four scenes and 64 tuning frames from two. Adjacent video frames are correlated, so extra rooms are more useful for assessing generalization than simply collecting more consecutive frames in the same room. We therefore acquired a new, bounded sample from the pinned training-shard revision, not the 654-image evaluation collection. It is still NYU-derived data, not a new independently captured dataset.

**Source and sampling.** `configs/data_2026-11-14_diverse_nyu.json` fixed the acquisition before the full run. `scripts/acquire_diverse_nyu.py` obtains archive sizes from the pinned revision, selects eight evenly spaced, 512-byte-aligned windows per shard, and requests 32 MiB from each window. The source archives are uncompressed tar: file headers occur at 512-byte boundaries. The parser finds checksum-valid headers, accepts complete regular `.h5` members with safe paths, validates RGB/depth shapes, and chooses at most 24 evenly spaced members from each window. Range response status, offsets, expected shard size, member offsets, local SHA-256 hashes and any retry errors are recorded. The script excludes exact scene names used in the earlier six-scene experiments. This procedure samples across archive positions, not uniformly across all frames or scenes; a scene crossing a window boundary or shard can be represented unevenly. The current mirror's full upstream archive bytes were not independently verified because only byte ranges were fetched.

**Pilot, finding and correction.** A one-window-per-shard pilot obtained 48 pairs across 12 named scenes. The full acquisition produced 2,304 pairs in 125 named scenes with zero failed range requests; it is preserved at `data/nyu_depth_v2/diverse_2026-11-14/`. The first split treated complete names as separate scenes. A subsequent name audit found `kitchen_0045a`/`kitchen_0045b` and `furniture_store_0002b`/`furniture_store_0002d` across training/tuning, and `basement_0001c` potentially related to an earlier `basement_0001a`. We do not know that each suffix pair truly represents the same room, so we conservatively group them rather than assert a confirmed duplicate. The first split is historical and is **not** the active training split.

**Regrouping.** `configs/data_2026-11-14_diverse_regroup.json` records the response before creating a new split. `scripts/regroup_nyu_scenes.py` strips lowercase letter suffixes following the final numeric scene identifier, assigns the resulting location groups to train/tune with seed 42, and excludes location-group keys from the earlier expanded experiment. It copies samples into `data/nyu_depth_v2/diverse_2026-11-14-regrouped/`, checking source and copied-file hashes. The result is 1,857 training pairs from 98 named scenes and 445 tuning pairs from 26 named scenes. `basement_0001c` was excluded as a possible earlier-location match. Different identifiers may still refer to the same real place; this rule is a conservative heuristic, not authoritative metadata. Prior scene tuning images were excluded to reduce contamination, but prior evaluation scene identities are unknown.

**Commands:**

```bash
bash scripts/python.sh scripts/acquire_diverse_nyu.py --windows-per-shard 8 --window-mib 32 --per-window 24 --output data/nyu_depth_v2/diverse_2026-11-14
bash scripts/python.sh scripts/regroup_nyu_scenes.py --manifest data/nyu_depth_v2/diverse_2026-11-14/manifest.json --exclude-manifest data/nyu_depth_v2/multiscene_2026-11-14-expanded/manifest.json --output data/nyu_depth_v2/diverse_2026-11-14-regrouped
bash scripts/python.sh scripts/verify_scene_split.py --manifest data/nyu_depth_v2/diverse_2026-11-14-regrouped/manifest.json --output results/data/2026-11-14-diverse-regrouped-overlap.json
bash scripts/python.sh scripts/audit_near_duplicates.py --manifest data/nyu_depth_v2/diverse_2026-11-14-regrouped/manifest.json --output results/data/2026-11-14-diverse-near-duplicates.json
```

The exact audit hashes decoded RGB and depth, checks all manifest-file hashes and tests training/tuning/evaluation exact RGB overlap. It found no exact decoded RGB matches across these groups. A separate 64-bit difference-hash audit compares 9×8 grayscale luminance differences and flags Hamming distance ≤3; across 826,365 training–tuning, 1,214,478 training–evaluation and 291,030 tuning–evaluation pairs, it flagged none. The minimum distances were 7, 7 and 8 respectively. This is a screening tool: similar hash does not prove duplication, and dissimilar hashes cannot rule out near-duplicate images or shared scene identities. The independently generated `results/data/2026-11-14-diverse-group-audit.json` verifies no overlap of the inferred location-group keys and lists scene types. It does not verify the real-world identities of locations. Avoid using the historical split for training or repeatedly selecting models on the 654 evaluation images.

**Defense:** Why group scene suffixes? The names suggest separate recordings may refer to the same location, so keeping their common prefix in one split reduces a plausible leakage risk. Why check near duplicates as well as exact hashes? Camera frames can differ by small motion or lighting and still depict essentially the same scene. Why is the test imperfect? A tiny perceptual hash can both collide for unrelated images and miss genuine similar views; scene metadata and manual review provide stronger evidence.

## Original NYU evaluation-scene identity investigation — 14 November

The [official NYU labeled dataset documentation](https://cs.nyu.edu/~fergus/datasets/nyu_depth_v2.html) identifies `images`, `depths`, `scenes`, raw filenames and metric-depth units in the original MATLAB file. A bounded HEAD check found that file reachable and about 2.97 GB, while the original FastDepth data endpoint timed out on the checked HTTP and HTTPS attempts. Reachability is not a checksum or provenance proof. See `results/data/2026-11-14-provenance-head-check.json`.

`scripts/audit_official_nyu_identity.py` reads a bounded portion of the official file using validated HTTP byte ranges, without downloading it in full. On the first 16 official labeled indices, six appeared in the local 654-file collection and their RGB arrays matched **exactly** after transposing official `3×640×480` storage to local `3×480×640`; their local five-digit names equal the one-based official indices. See `results/data/2026-11-14-official-prefix16.json`. This is evidence for, not complete proof of, the filename-to-index mapping.

`scripts/audit_nyu_scene_mapping.py` uses that mapping as an explicitly **inferred** hypothesis and reads official scene metadata for all 654 numeric local filenames. It inferred 215 distinct evaluation scene names and found no matching suffix-normalized scene groups in our new training or tuning split. The complete inferred mapping is `results/data/2026-11-14-inferred-evaluation-scenes.json`. An additional 32 evenly spaced local filenames were checked against their hypothesized official indices: **31 matched exactly** (`results/data/2026-11-14-official-even32.json`). The remaining local file `00567.h5` was not byte-identical to official index 566, though 99.57% of its RGB byte values matched; the maximum per-byte difference was 89 (`results/data/2026-11-14-official-00567-diagnostic.json`). This is evidence of a very similar image, not an exact match, and the cause of the differences is unknown. Most of the 654 images have not been individually verified; the naming convention and group-normalization heuristic could be wrong, and real places can have different names. Thus this improves the investigation but does not establish complete test identity or checkpoint pretraining separation.

## Why do we have so few training images? (14 November)

The local 654 files are validation/evaluation material, so using them to fit weights or rank pruning candidates would compromise that comparison. We do not have the complete NYU training collection locally: the pinned mirror exposes twelve training tar shards, the first eleven roughly 3 GB each and the last roughly 1.1 GB. Earlier bounded requests retrieved only short prefixes to make a usable pipeline quickly, leaving 16 training and 16 tuning images. That was an acquisition choice, not a property of NYU. For a broader exploratory subset, `scripts/acquire_multiscene_subset.py` requests the beginning of six distinct pinned shards and extracts the first eight HDF5 samples from the first scene in each: four scenes/32 images for training and two scenes/16 images for tuning. This deterministic convenience sample is not a random or representative NYU sample; nearby frames in each scene may be highly correlated. The pinned revision, byte ranges, scene names, original member paths and sample hashes are in `data/nyu_depth_v2/multiscene_2026-11-14/manifest.json`.

`scripts/verify_scene_split.py` checks the manifest hashes, verifies that the declared scene names match sample member paths and that training/tuning scene names are disjoint, and tests decoded RGB hashes against each other and the 654 evaluation files. `results/data/2026-11-14-multiscene-overlap.json` reports no exact RGB matches. This does not detect near-duplicates or prove evaluation-scene separation, because evaluation scene identities are unknown. The bedroom_0017 scene was used for tuning in a prior exploratory experiment and is now used for training; do not treat results across those experiments as independent. The source is a mirror and the downloaded archive prefixes have no independent per-member upstream checksum; the recorded sample hashes support future reproducibility, not proof of original NYU identity. A larger acquisition was also attempted separately; consult the progress report for its actual outcome.

The larger acquisition succeeded: `data/nyu_depth_v2/multiscene_2026-11-14-expanded/manifest.json` contains 32 images per scene, or 128 training and 64 tuning images; its overlap audit is `results/data/2026-11-14-expanded-overlap.json`. It covers the same six scenes and includes the earlier eight images per scene, so it increases frames but not scene diversity. This expanded manifest was chosen for matched training and tuning after the initial ablation scoring, before inspecting any of the new tuning results; the score still uses the original 32 training images. `configs/experiment_2026-11-14_expanded_recovery.json` records the protocol amendment. The command was `bash scripts/python.sh scripts/acquire_multiscene_subset.py --per-scene 32 --prefix-mib 48 --output data/nyu_depth_v2/multiscene_2026-11-14-expanded` followed by `bash scripts/python.sh scripts/verify_scene_split.py --manifest data/nyu_depth_v2/multiscene_2026-11-14-expanded/manifest.json --output results/data/2026-11-14-expanded-overlap.json`.

## Dataset structure and purpose

The local validation directory contains 654 HDF5 files. Each inspected sample has an RGB array stored as channels-first `3 × 480 × 640` unsigned bytes and a `480 × 640` floating-point depth array. HDF5 stores named datasets inside each file; `rgb` and `depth` must refer to the same scene. We have not yet established that these file identities exactly match the authors' standard split, or independently confirmed the depth units. A count of 654 alone is not proof of either.

A training set supplies examples used to adjust weights. A tuning set selects hyperparameters or pruning candidates. A final evaluation set is reserved for measuring the frozen method. Mixing these roles leaks information and makes results optimistic. The training/tuning subsets and overlap checks are not yet available.

## Implemented validation transform

The upstream validation code first scales height 480 by `250/480`, then center-crops `228 × 304`, then resizes to `224 × 224`. It uses nearest-neighbor interpolation. The original `scipy.misc.imresize` and `numpy.asfarray` are unavailable in the installed modern libraries, so `src/fastdepth_project/data.py` uses Pillow nearest-neighbor resize and NumPy conversion. It scales RGB bytes to `[0,1]`, rearranges HWC to CHW, and preserves depth as floating point. For 480 × 640 input, the intermediate size is 250 × 333; the crop starts at row 11, column 14 under Python's rounding rule.

RGB and depth receive the same geometric operations so corresponding pixels remain aligned. Nearest-neighbor picks a source pixel instead of averaging neighboring depths; changing interpolation changes evaluation. Constant-image and shape tests pass, but exact parity against the old SciPy implementation and the sample identities remain unverified. Consequently any initial accuracy results are provisional, and their depth units are described as native dataset units rather than asserted metres.

Run `bash scripts/python.sh scripts/evaluate_validation.py --output <new-directory>` to record an evaluation manifest, per-image results and a summary. The directory must not already exist, preventing an earlier run from being overwritten. The audit at `results/data/2026-11-13-validation-audit/` read all 654 files, found one common schema, no read errors and no duplicate full-file SHA-256 hashes. Every inspected depth value was positive and finite; observed positive values ranged from approximately 0.7133 to 9.9866 native units. Exact file hashes cannot establish scene-level separation or rule out near-duplicate images. The histogram is saved as `depth_distribution.png`; depth units and original split identity remain unverified.

## Source identity and preprocessing verification — 13 November

The two local validation archives have SHA-256 values matching the Hugging Face dataset's pinned revision `50579a0b591445f91bf7269b28611ad1cc6a05d2`; every one of the 654 extracted HDF5 files was compared byte-for-byte by hash with its archive member. The [dataset card](https://huggingface.co/datasets/sayakpaul/nyu_depth_v2/blob/50579a0b591445f91bf7269b28611ad1cc6a05d2/README.md) says the copy was sourced from FastDepth. That establishes our mirror's provenance and local archive integrity, not independent equality to the inaccessible original MIT archive or the precise benchmark identities.

The original [NYU dataset documentation](https://cs.nyu.edu/~fergus/datasets/nyu_depth_v2.html) states that its labeled depth arrays are in metres. The local data's values, mirror attribution, and closeness to the checkpoint's historical metrics are consistent with metres, but they do not independently establish that every stage in the mirrored HDF5 conversion preserved the scale. We continue to label these values native units until that chain is verified.

To check resizing, `scripts/verify_preprocessing.py` extracts the `bytescale`, `toimage`, `fromimage` and `imresize` function bodies from [SciPy 1.1.0 source](https://github.com/scipy/scipy/blob/v1.1.0/scipy/misc/pilutil.py). Old decorators are removed, the deleted NumPy `tostring` alias is replaced by `tobytes`, and Pillow's removed type-check helper is shimmed. Five real validation samples plus a seeded synthetic pattern produced identical resized RGB bytes and float depth values. RGB float64 normalization differed from our float32 intermediate by at most 2.97e-8 before conversion; after the upstream `ToTensor.float()` cast, the final tensors matched exactly in all six cases. This uses **current** NumPy/Pillow, not a complete 2018 binary environment. The first comparison attempt failed because modern NumPy removed `ndarray.tostring`; the corrected compatibility shim produced the recorded result. Source, BSD license and result are preserved under `results/data/2026-11-13-source-verification/`.

## Small scene-grouped training sample

Pinned HTTP byte ranges from training shards 0 and 1 provided 16 frames from `basement_0001a` and 16 from `bedroom_0017`. The first group is training and the second tuning. `scripts/verify_scene_split.py` confirmed distinct scene-name strings, verified file SHA-256 values and found zero exact decoded RGB matches across training/tuning or against the 654 local validation images. Exact hashes cannot rule out near-duplicates, and validation scene identities remain unknown. The first acquisition attempt had a relative-versus-absolute path error; its `failure.json` and partial file are retained, while the corrected run uses a separate output directory.

The upstream training loader also excludes filenames containing `00001.h5` and `00201.h5` for its internal holdout; our fixed tiny scene-grouped training sample includes `00001.h5`. Thus it is a project-specific exploratory split, not an exact recreation of the original training split. A single scene per group is much too narrow for a generalization claim.
